# 真机抽验检查点矩阵

vcan 上的自动化能证明软件自洽，证明不了它跟真 ECU 讲得通。本文是**里程碑合入前**在真机上逐条打勾的清单（[requirements.md](requirements.md) 验收口径的档三）。

用法：每项按"怎么查"执行，按"通过判据"判红绿，把结果与 ECU 型号、固件版本、通道记在表格末尾。**未执行的项必须标"未验"，不能留空** —— 空行与绿行在复盘时长得一样。

## 前置条件

| 项 | 要求 | 不满足时的处理 |
|---|---|---|
| 硬件 | 周立功 CAN-FD 卡（Windows 侧驱动已装）；目标 ECU 与线束可上电 | 抽验整段标"未验"——里程碑可勾，但不得声明抽验通过 |
| 软件路径 | Windows 侧 `bus-zlg`（M4 末尾落地）或 Linux socketcan，二选一 | 无可用路径等于抽验无法执行，同样整段标"未验"；记录实际走了哪条 |
| 写入备份 | `--state-dir` 目录可写；抽验前记下 ECU 里被写标定量的初值 | 目录不可写时写入会在落快照那一步失败——先修目录，别绕过 |
| 通道 | 至少一条 CAN 或 CAN-FD 通道，波特率已知 | 记录实际波特率，不要按默认为 500 kbit/s 假定 |
| 标识符 | ECU 的 CRO / RES 标识符（XCP 从站配置或 ECU 文档） | 缺失时先用扫描法在检查点 H-05 里试探 |
| 信息源 | 带 A2L 时准备 A2L；仅 ELF 时准备未 strip 的 ELF | 两者都没有时只验证链路与协议（M3 之前无变量模型） |

Linux 侧经 socketcan 访问同一张卡时，Windows 驱动与 socketcan 不能同时占用同一通道 —— 抽验前确认占用方。

## 一、链路层（H-01 ~ H-05）

| 编号 | 检查什么 | 怎么查 | 通过判据 | 失败常见原因 |
|---|---|---|---|---|
| H-01 | 通道枚举 | `openape probe bus --json` | 目标通道出现在 `channels` 里 | 驱动未装、通道名大小写不符 |
| H-02 | 打开与能力位 | `openape probe bus --channel <ch> --json` | 能打开；`can_fd` 与 `hardware_timestamp` 与驱动实际能力一致 | 能力位报 false 但驱动支持——说明后端未接，不是 bug，但要在记录里注明。socketcand 后端按接口 MTU 上报 FD（`mtu >= 72`，与内核发送路径同判据）：真机上核 `ip -d link show <ch>` 的 MTU 与 `can_fd` 是否对得上；`hardware_timestamp` 目前各后端一律报 false（软时间戳路径） |
| H-03 | 经典帧自发自收 | 两个终端各跑一次 `probe bus --channel <ch>` 后手工发帧，或用外部工具发一帧 | 对端能收到，DLC 与数据一致 | 未接线、终端电阻缺失、波特率不一致 |
| H-04 | 8 字节填充策略 | 抓包看 ECU 回的响应帧 DLC | 记录 ECU 是否满帧填充 | 填充与否不影响解析，但影响"响应是否被截断"的判定，必须记录 |
| H-05 | 标识符确认 | 按已知配置跑 `probe xcp`；不确定时在 0x600/0x601 附近试探 | 能建链 | 标识符错、ECU 未进入可标定状态 |

## 二、XCP 传输层（H-06 ~ H-10）

| 编号 | 检查什么 | 怎么查 | 通过判据 | 失败常见原因 |
|---|---|---|---|---|
| H-06 | 建链 | `openape probe xcp --channel <ch> --tx-id <id> --rx-id <id> --json` | 退出码 0，`max_cto` / `max_dto` 与 ECU 文档一致 | ECU 需要先上电时序或诊断会话 |
| H-07 | 命令码回显 | 同上，同时用 `--frame-trace` 看响应帧 | ECU 的响应 `[PID, 命令码, 参数]` 回显了请求命令码 | 若 ECU 不回显（部分实现），记为"非标准回显"，这会触发 `[2002]` 协议错误，需要后端适配位 |
| H-08 | 超时与重发 | 拔掉 ECU 或断电后跑 `probe xcp --timeout-ms 100` | 退出码 20，报"等待超时"，给出建议 | 需确认重发不导致 ECU 状态异常 |
| H-09 | 错误码表 | 故意读一个越界地址 | 退出码 20，消息里带 ECU 返回的错误码原文 | ECU 用的是非标准错误码表 —— 记录下来，不要按已知表猜测 |
| H-10 | 时序余量 | 连续跑 `probe xcp` 10 次 | 10 次全成功 | 偶发失败说明超时余量不足，记录具体失败次数 |

## 三、协议语义（H-11 ~ H-14）

| 编号 | 检查什么 | 怎么查 | 通过判据 | 失败常见原因 |
|---|---|---|---|---|
| H-11 | 短读 | `openape read --channel <ch> --address <addr> --len 4` | 退出码 0，返回 4 字节 | 地址未映射、ECU 只允许读标定段 |
| H-12 | 长读分段 | `--len 16` | 一次调用返回 16 字节，内部走 SET_MTA + UPLOAD | UPLOAD 的地址推进语义与标准不符会在此暴露 |
| H-13 | 读值与信息源对照 | 用 A2L 里某个已知标定量的地址与初值比对 | 读回值与 A2L 初值/工具显示一致 | 端序、地址是逻辑段偏移而非绝对地址 |
| H-14 | 页切换 | 有双页的 ECU：切页后再读同一地址 | 读值随页变化，切回原页后恢复 | 页号编码差异（单字节 vs u16）——记录 ECU 实际编码 |

## 四、标定作业前的基础确认（H-15 ~ H-17）

| 编号 | 检查什么 | 怎么查 | 通过判据 | 失败常见原因 |
|---|---|---|---|---|
| H-15 | 设备独占锁 | 一个终端持有 daemon/CLI，另一个终端再跑 `probe xcp` 同一通道 | 后者报"已被进程 N 占用"并给建议 | 锁文件残留（PID 已死应能自动回收） |
| H-16 | 帧级记录可用 | `--frame-trace` 跑一次读 | stderr 里能看到收发两个方向、标识符与字节 | 记录量过大导致终端阻塞 —— 记下实际帧率 |
| H-17 | 故障信息可用性 | 故意制造一次失败（拔线/错标识符） | 报出稳定编号、可读消息、可操作建议，退出码按域分段 | 提示不够具体就是 issue，不是"能用就行" |

## 五、写入类（H-18 ~ H-24）

> 写入是本软件唯一会改变 ECU 状态的操作，所以这一节每条都要**先备份**：
> 写前快照由软件自动落盘（`--state-dir` 下 `snapshots/`），确认它存在再继续。

| 编号 | 检查什么 | 怎么查 | 通过判据 | 失败常见原因 |
|---|---|---|---|---|
| H-18 | 单点写与读回 | `openape write --channel <ch> --symbol <sym> --value <v> --elf <f> --json` | 退出码 0；`before_hex` 与写前读值一致，`after_hex` 与写入值一致 | 地址落在只读段、资源未解锁 |
| H-19 | 写前快照与审计 | 同上，检查 `snapshot_path` 指向的文件与 `--state-dir/write-audit.jsonl` | 快照里存的是写前值；审计有一条，含 actor、时刻、写前写后值 | 目录不可写、两档标记不一致 |
| H-20 | 量程拦截 | 带 A2L 的标定量写一个越界值 | 退出码非 0，消息含 min/max 与实际值，ECU 里的值未变 | 该标定量在 A2L 里没有 `LOW_LIMIT`/`UPPER_LIMIT` |
| H-21 | 解锁流程 | 对受保护的 ECU 先直接写，再 `probe`/`unlock` 后重写 | 直接写报需要解锁并给建议；解锁后写入成功 | 密钥算法与 ECU 不匹配（默认示例算法只对自研从站有效） |
| H-22 | 页切换与页对比 | `openape page set --page 1`，再 `page diff --reference 0 --working 1 --elf <f>` | 切页读回一致；diff 只列差异地址，空差异明说"一致" | 页号编码差异、ECU 不支持双页 |
| H-23 | 按项复制 | 用界面或 CLI 从参考页复制单个标定量到工作页 | 只有被确认的项变了，其它项不动 | 误用整页覆盖（本版本没有整页入口） |
| H-24 | 回滚 | `openape dataset restore --snapshot <file> ...` | 写回后读值与快照一致，审计多一条且 actor 标"回滚" | 快照档位与当前不符 |

软件路径为 Windows `bus-zlg` 时，H-18 ~ H-24 还要额外确认 `probe bus` 的能力位与会话参数；Linux 侧同组检查点用 socketcan 跑一遍即可。

## 与自动化测试的边界

| 能由 vcan 覆盖 | 只能在真机确认 |
|---|---|
| 命令编解码字节、对齐规则、错误码映射 | ECU 的填充策略与回显习惯 |
| 建链、短读、长读、页切换的软件链路 | 真实时序余量、偶发失败率 |
| 设备锁、退出码、故障文案 | 硬件能力位与驱动行为 |
| 从站模拟器的行为 | 目标 ECU 的怪癖（属 M5 怪癖配置层） |
| 写入的软件链路：写前读回、分块、读回校验、量程拦截、快照、审计、回滚、页间 diff | 真 ECU 的写保护与解锁算法、页号编码、写入速度与掉电行为 |
| Windows 后端的"平台不支持"分支与非 Windows 平台行为 | `zlgcan.dll` 的实际句柄行为与 CAN-FD 时序（`bus-zlg` 的 Windows 侧未在 Linux 上编译验证） |
